# Архитектура: bitrix24-leads

```
Telegram: /start → «Оставить заявку» → FSM: имя → телефон → что нужно → подтверждение
                                                │
                                                ▼
crm.submit(name, phone, need)
   ├─ crm.settings.mode.get → классический (лиды) / простой (контакт + сделка)
   ├─ crm.duplicate.findbycomm(PHONE) → есть ли лиды/контакты с этим номером
   ├─ открытая заявка есть → crm.timeline.comment.add (без новой записи)
   ├─ клиент известен → новая заявка «Повторное обращение» + привязка к контакту
   └─ новый → лид (классический) или контакт + сделка (простой)
                                                │
          ошибка связи с CRM → outbox (SQLite) → retry_outbox() раз в минуту
                                                │
менеджеру в Telegram: что за заявка + ссылка на карточку в Битрикс24
```

## Модули
| Модуль | Что делает |
|---|---|
| `b24.py` | Клиент REST через входящий вебхук; повтор при QUERY_LIMIT_EXCEEDED (лимит ~2 запроса/с) |
| `crm.py` | Нормализация телефона, настройка CRM (источник, поля), заявка без дублей в обоих режимах |
| `outbox.py` | Очередь заявок при недоступной CRM (до 60 попыток, дальше — разбор вручную) |
| `bot.py` | Форма (aiogram FSM), отправка в CRM, уведомления менеджеру, досылка из очереди |

## Решения и почему
- **Режим CRM определяется, а не предполагается.** Первая версия работала только с лидами — на свежем портале
  (простой режим по умолчанию) Битрикс сам превращал каждый лид в контакт + сделку, и проверка «есть ли открытый лид»
  ничего не находила: дубли создавались. Живой тест это поймал; теперь `crm.settings.mode.get` и две ветки логики.
- **Дубли — по нормализованному телефону.** «8 (913) 000-11-22» и «+79130001122» — один клиент.
- **Повторная просьба — комментарием, а не новой заявкой**, пока прошлая открыта: менеджер видит всю историю в
  одной карточке и не звонит клиенту дважды.
- **Свой контакт, а не чужой.** Кнопка «Поделиться номером» шлёт контакт; если это контакт другого человека,
  бот просит свой.
- **Очередь при недоступной CRM.** Клиент не должен получать ошибку из-за техработ у Битрикс24. Повторы ограничены:
  постоянная ошибка (например, у вебхука отобрали права) не крутится вечно.
- **Настройка CRM идемпотентна** — источник и поле создаются, только если их нет; поле создаётся и для лидов, и для
  сделок, потому что режим портала могут переключить.
- **Права вебхука проверяются явно** (`scope.json`): при первом подключении вебхук был без прав — `insufficient_scope`
  на любой метод CRM, хотя галочка «вроде бы» стояла.
